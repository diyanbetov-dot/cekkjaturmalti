Implementation Plan: Long-Text Spellchecker Performance

Goal

Reduce long-text requests from the current 50-65 second range to a bounded
few-second response without weakening deterministic Maltese corrections,
grammar rules, crucial suggestions, or displayed meanings.

Current Code Structure and Main Cost Centres

- correct_text_rich in Essentials/app.py already resets request-local token
  and suggestion caches, enables bulk mode, tokenises text, applies phrases,
  and builds rich frontend tokens.
- correct_word runs the X/Y/Z correction pipeline for each word.
- suggest runs the W-stage alternative/suggestion work.
- _get_candidates_cached still has a length-based fallback that iterates the
  dictionary when anchor candidates are scarce.
- Long texts can repeatedly trigger candidate generation, suffix analysis,
  phrase logic, and suggestion work for words which do not need a visible
  alternative.

Phase 1: Establish a Performance and Quality Baseline

1. Add structured timing/counter instrumentation for each request:
   - word count and unique normalized token count;
   - correct_word, suggest, phrase-rule, suffix, and meaning timings;
   - anchor candidate counts and dictionary-fallback counts;
   - cache hit/miss counts.
2. Add the supplied long supermarket/toilet text as a performance fixture.
3. Preserve existing short-word, paragraph, grammar, suggestion, and UI
   regression tests as quality snapshots.
4. Record corrected text, suggestions, crucial flags, meanings, and
   unrecognized flags for each snapshot before optimisation.

Solves:
- Identifies the actual bottleneck rather than guessing.
- Prevents performance work from silently reducing linguistic quality.

Phase 2: Make Deterministic Work Cheap

1. Reuse request-local TokenAnalysis for every repeated normalized token.
2. Reuse context-independent suffix and candidate analysis within a request.
3. Do not call suggest merely because correct_word changed a word.
4. Generate alternatives only where multiple verified corrections exist.
5. Reuse phrase/article results instead of repeating correction for words
   already analysed in the same request.

Solves:
- Repeated words such as il, ghax, trolley, partner, and common articles no
  longer pay for the full analysis repeatedly.
- Maintains the existing X/Y/Z correction behaviour.
- Avoids unnecessary W-stage work while keeping true ambiguity visible.

Phase 3: Bound and Accelerate Fuzzy Candidate Search

1. Add RapidFuzz as the native accelerated distance/ranking backend.
2. Keep current Maltese anchor buckets, special-character restrictions,
   consonant rules, and suffix verification as the source of truth.
3. Replace only slow Python Damerau-Levenshtein comparison/ranking paths.
4. Use strict score cutoffs and hard candidate limits.
5. Stop candidate search as soon as a verified close correction wins.
6. Keep W-stage fuzzy output as suggestions only; never allow it to silently
   replace a word with a distant candidate.

Solves:
- Unknown/noisy tokens no longer trigger broad slow scans.
- Retains existing linguistic safeguards and correction quality.
- Makes candidate ranking fast without relying on a generic English checker.

Phase 4: Remove Full-Dictionary Fallback Scans

1. Build immutable startup indexes for:
   - consonant anchors;
   - word length plus initial letter;
   - special-character-normalized forms;
   - paradigm/verb root groups where useful.
2. Replace the loop across self.dictionary in _get_candidates_cached with
   bounded lookup in the relevant prebuilt bucket.
3. Optionally evaluate marisa-trie for the immutable exact dictionary and
   prefix lookups, primarily to lower memory use.
4. Keep the ordinary Python set/dict indexes if benchmarks show they are
   faster for the frequent exact lookup path.

Solves:
- Removes the main worst-case path for one unfamiliar word.
- Reduces Cloud Run memory pressure without sacrificing dictionary coverage.

Phase 5: Give Long Text Its Own Safe Execution Policy

1. Define a clear long-text threshold based on word count, not characters.
2. For long text, retain every X/Y/Z deterministic correction path.
3. Run W only for:
   - unrecognized words;
   - crucial ambiguities;
   - tokens with two or more verified close alternatives.
4. Generate meanings only for alternatives that will actually be displayed.
5. Put a small budget on expensive work per unique unresolved token.
6. When the budget is exhausted, leave a genuinely unresolved word red rather
   than attempting a distant or low-quality correction.

Solves:
- Long posts retain spelling and grammar correction quality.
- Low-value popovers no longer consume most of the request time.
- Prevents one bad token from causing a gateway timeout.

Phase 6: Optional Fixed-Rule Accelerator

1. Evaluate pyahocorasick for large exact sets of manual spellings,
   contractions, lexicalized expressions, and fixed multiword phrases.
2. Build and serialise the automaton at startup.
3. Use it only for deterministic exact-rule detection before ordinary word
   analysis.
4. Do not use it to replace morphology, suffix generation, or grammar rules.

Solves:
- Finds many known fixed patterns in a single pass.
- Keeps manual/lexical rules fast as their data files grow.

Phase 7: Sentence Parallelism Only After Bounding Per-Token Work

1. Split text at existing sentence boundaries.
2. Preserve boundary-sensitive context, capitalization, and punctuation.
3. Process only independent sentence chunks with a small bounded executor.
4. Merge tokens and corrected text in original order.
5. Benchmark one worker, two workers, and the Cloud Run CPU allocation before
   enabling it by default.

Solves:
- Improves throughput on multi-core Cloud Run instances.
- Avoids memory multiplication and CPU contention from unbounded workers.

Verification Criteria

1. All correction/grammar/suggestion regression snapshots retain their output.
2. The supplied long text completes locally and on Cloud Run within the chosen
   gateway limit.
3. No request performs a whole-dictionary scan for each unrecognized token.
4. The service remains below its deployment memory limit.
5. The frontend still displays crucial suggestions and red unrecognized words
   correctly.

Recommended Implementation Order

1. Phase 1: profiling and baseline.
2. Phase 2: cache and suggestion gating.
3. Phase 4: bounded candidate indexes.
4. Phase 3: RapidFuzz integration and comparison benchmarks.
5. Phase 5: long-text policy.
6. Phase 6: optional Aho-Corasick optimisation.
7. Phase 7: optional sentence-level parallelism.
