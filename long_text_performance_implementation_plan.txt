# Long-Text Spellchecker Performance Plan

## Goal

Reduce long-text requests from the observed 50-65 second range to a bounded
few-second response without weakening deterministic Maltese corrections,
grammar rules, crucial suggestions, displayed meanings, capitalization,
punctuation, or red unresolved-word behaviour.

This plan treats correctness as the contract. Performance changes must make the
same linguistic work cheaper and more bounded, not silently lower quality.

## 1. Stabilize Correctness First

Fix all remaining phrase-boundary and related correctness regressions, then run
the full existing test suite.

Review and approve the corrected outputs before freezing them. Do not preserve
known incorrect behaviour merely because it existed before optimization.

Freeze the approved outputs into rich-token regression snapshots covering:

- corrected text;
- token boundaries;
- choices and suggestions;
- meanings;
- crucial flags;
- grammar findings and safe rewrites;
- unrecognized state;
- capitalization and punctuation;
- phrase and article behaviour.

Treat this approved snapshot suite as the linguistic quality contract throughout
optimization. Any intentional output change must be documented and approved
rather than silently updating the snapshot.

## 2. Profile the Real Bottleneck

Extend the existing `RequestProfiler`; do not create a separate profiling
system.

For each request, measure:

- total request duration;
- total and unique normalized token counts;
- repeated-token cache hits and misses;
- time spent in `correct_word`;
- time spent in `suggest`;
- dictionary entries inspected;
- anchor entries inspected;
- candidate counts;
- candidates scored;
- distance calls;
- suffix work;
- phrase work;
- X-, Y-, Z-, and W-stage calls;
- grammar analysis and rewrite passes;
- meaning lookups;
- rich-token construction time;
- the five slowest unique tokens, including their slowest stages.

Count entries inspected separately from candidates returned. Returning only 32
candidates does not prove that only 32 dictionary entries were examined.

Repair any recoverable CP1252/UTF-8 mojibake in supplied benchmark text with
`Other/tools/repair_mojibake.py`, verify the Maltese letters, then save the
fixture as UTF-8.

Add the exact long paragraph that currently takes approximately 50-65 seconds
as a benchmark fixture.

Benchmark it through:

1. the internal correction function;
2. the local Flask endpoint;
3. the deployed Cloud Run candidate revision.

Keep Netlify or other external routing latency separate from
correction-processing time.

Perform one warm-up run followed by at least five measured local runs. Record
best, median, mean, and worst durations before making performance changes.

## 3. Remove Unbounded Retrieval

Replace the request-time fallback iteration over `self.dictionary` with
immutable startup-built indexes based on:

- Maltese grapheme length;
- initial grapheme;
- compatible special-character-normalized form;
- optionally the first two graphemes where useful.

Retrieve only plausible bounded buckets, normally covering the input grapheme
length and neighbouring lengths permitted by the existing correction rules.

Replace broad `anchor_map` traversal with:

- directly generated one-edit anchors;
- bounded anchor buckets based on grapheme length and compatible initial
  structure;
- existing Maltese linguistic restrictions.

Enforce hard limits for:

- buckets inspected;
- dictionary entries inspected;
- anchors inspected;
- raw candidates collected;
- candidates scored.

Add test assertions proving that no ordinary or long-text request scans the
complete dictionary or complete anchor map.

## 4. Consolidate Existing X/Y/Z/W Analysis

Keep one immutable, context-independent lexical `TokenAnalysis` per normalized
token per request.

Normalize cache keys consistently for:

- case;
- Unicode form;
- apostrophe variants;
- Maltese special characters;
- other existing equivalent input forms.

Reuse:

- exact dictionary lookup;
- candidate retrieval;
- candidate distance results;
- suffix analysis;
- morphology;
- verified lexical corrections.

Keep the following outside the normalized lexical cache:

- original capitalization;
- sentence-initial status;
- punctuation;
- token position;
- neighbouring-token context;
- phrase logic;
- articles and prepositions;
- `i-`/`u-` contextual state;
- grammar context;
- final surface formatting.

Reuse phrase results when a phrase rule has already consumed or resolved
tokens. Do not send consumed tokens through the complete independent correction
pipeline again unless a later stage genuinely requires it.

Avoid unnecessary deep copies where cached analysis is immutable.

## 5. Gate Expensive Suggestions and Meanings

Keep deterministic X/Y/Z correction behaviour unchanged.

Run the W stage only when at least one of these applies:

- the word remains unresolved;
- a crucial ambiguity applies;
- an explicit suggestion override exists;
- two or more verified close candidates exist;
- a known ambiguity rule requires visible alternatives.

Do not run W merely because the automatic correction differs from the original
token.

W-stage fuzzy results must remain suggestions only and must never silently
replace a word with a distant or weakly supported candidate.

Compute meanings only after the final visible choice list has been selected.

Bound:

- candidates scored;
- choices displayed;
- meaning lookups.

Preserve every known crucial alternative and its displayed meaning.

## 6. Consolidate Grammar Work

Ensure the full grammar analysis normally runs once per corrected request.

Reuse the resulting findings for:

- safe rewrite selection;
- token metadata;
- frontend grammar information;
- diagnostics.

Do not analyse the complete unchanged text repeatedly inside separate grammar
methods.

When post-rewrite validation is necessary, revalidate only:

- affected sentences;
- affected token ranges;
- affected rule families.

Profile full grammar passes separately from limited post-rewrite validation.

Add an assertion or profiler warning when an ordinary request unexpectedly
performs multiple full-text grammar analyses.

## 7. Integrate RapidFuzz Carefully

Add RapidFuzz behind a feature flag only after candidate retrieval has been
bounded.

If comparison confirms that the current custom distance function implements
Optimal String Alignment, use RapidFuzz `OSA.distance`, not a different generic
Damerau-Levenshtein implementation.

Pass the existing Maltese grapheme sequence rather than raw characters so units
such as `għ` retain their present treatment.

Compare the old and new implementations across all snapshots for:

- distance values;
- score cutoffs;
- transpositions;
- apostrophes;
- Maltese special characters;
- candidate ordering;
- chosen corrections;
- displayed alternatives.

Use RapidFuzz only to calculate or rank distances within a small verified
candidate pool.

Apply strict score cutoffs and hard candidate limits.

Retain the existing implementation behind the feature flag until output and
ranking equivalence have been demonstrated.

## 8. Strengthen the Existing Long-Text Mode

Extend the current bulk mode rather than creating a separate spellchecker.

Long-text processing must preserve:

- exact recognition;
- manual deterministic corrections;
- all X/Y/Z corrections;
- phrase rules;
- suffix and morphology rules;
- grammar rules and safe rewrites;
- crucial choices;
- meanings for displayed choices;
- red unresolved words.

Add deterministic operation budgets per unique unresolved token, such as:

- maximum dictionary entries inspected;
- maximum anchor entries inspected;
- maximum candidate buckets;
- maximum candidates scored;
- maximum distance calls.

Prefer operation-count budgets over wall-clock cutoffs because they are
deterministic and testable.

When the budget is exhausted, leave the token unresolved and red rather than
selecting a weak correction.

One pathological token must not cause the rest of the paragraph to approach the
gateway timeout.

## 9. Evaluate Optional Packages Only After Measurement

Evaluate these only when profiling after the main changes still demonstrates a
need.

### `marisa-trie`

Benchmark it for immutable prefix indexes and memory reduction.

Retain Python sets and dictionaries for hot exact membership paths when they
remain faster.

### `pyahocorasick`

Use it only for large fixed collections of:

- exact replacements;
- lexicalized forms;
- contractions;
- fixed multiword patterns.

Do not use it to replace morphology, suffix generation, contextual grammar, or
fuzzy correction.

### Sentence Parallelism

Consider it only after the single-request path has bounded per-token work and
the deployed Cloud Run instance has useful multi-core CPU capacity.

Verify:

- phrase-boundary correctness;
- sentence-boundary context;
- deterministic output ordering;
- cache safety;
- memory use;
- actual speed improvement.

Do not assume Python threads will accelerate Python-heavy processing.

## 10. Deployment Verification

Use a candidate deployment path for Cloud Run performance verification:

1. Commit the candidate implementation locally.
2. Push it to a temporary candidate branch, for example
   `codex/long-text-performance`.
3. Build and deploy a Cloud Run candidate revision from that exact commit or
   image.
4. Route either no production traffic or a tiny controlled percentage to the
   candidate revision.
5. Benchmark the candidate revision directly.
6. Promote the exact verified commit to `main` only after the local and Cloud
   Run results are accepted.

This avoids the impossible requirement of benchmarking a deployed `main` build
before pushing the changes that Cloud Run needs in order to deploy them.

Benchmark warm and cold Cloud Run requests:

- one request at a time;
- several concurrent requests;
- ordinary short input;
- the real long fixture;
- an adversarial unresolved-token fixture.

Verify:

- the actual Docker startup command;
- whether `gunicorn.conf.py` is used;
- worker count;
- thread count;
- Cloud Run CPU allocation;
- memory allocation;
- request concurrency;
- timeout;
- cold-start time;
- warm processing time;
- peak memory under concurrent long requests.

Do not increase workers, threads, CPU, memory, or timeout as a substitute for
removing unbounded request-time work.

Confirm that the long fixture remains safely below the gateway timeout and that
concurrent requests do not produce unstable memory use.

## 11. Finish and Report

Run every correction, grammar, frontend-token, and performance regression test.

Report:

- baseline and final timings;
- best, median, mean, and worst durations;
- internal function time;
- local endpoint time;
- deployed Cloud Run candidate-revision time;
- dictionary entries inspected before and after;
- anchor entries inspected before and after;
- candidate and distance-call counts;
- W-stage calls before and after;
- grammar passes before and after;
- cache hits and misses;
- peak memory;
- the slowest remaining tokens and stages;
- all output changes;
- remaining performance limitations.

Commit and push to `main` only after:

- the complete regression suite passes;
- snapshot differences are reviewed;
- the local benchmark is recorded;
- the Cloud Run candidate revision benchmark is recorded;
- no full dictionary or anchor-map scan occurs.

## Definition of Done

The work is complete when:

- the approved correctness snapshots pass;
- the real long paragraph is reduced from the observed 50-65 second range to
  the best safely achievable few-second range;
- deterministic corrections and grammar behaviour are preserved;
- crucial alternatives and their visible meanings remain available;
- genuinely unresolved words remain red;
- repeated normalized tokens reuse lexical analysis;
- no request scans the complete dictionary;
- no request scans the complete anchor map;
- expensive W-stage work runs only when visible alternatives are needed;
- grammar analysis is not unnecessarily repeated;
- one pathological token cannot cause the entire request to time out;
- Cloud Run memory remains stable under concurrent testing;
- local and deployed results are documented.
